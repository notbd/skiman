# No crash-recovery journal

skiman keeps no write-ahead journal. The skill repo is under git, so a half-finished change can be inspected and reverted there; everything in tool directories is derived from the skill repo and `skiman sync` can rebuild it at any time; single entries are written under a temporary name and renamed into place. The one thing that cannot be rebuilt, the originals taken over during import, is moved into a backup before its replacement is created; a skill repo file import replaces (`skiman.toml`, `skiman.lock`, the shared body) has its old content written into the backup first, then the new file renamed over it in one step. Spec v8's per-scope journal and recovery table (§8) solved a problem this design no longer has.

What this promises is per entry: an entry skiman writes appears whole or not at all, and when a command is killed every original it was replacing is in its place, in the staging folder it was set aside to, or in a backup. On a filesystem with a rename that never replaces (APFS, HFS+, ext4, tmpfs, btrfs) a new entry also never goes over one that appeared in its place; elsewhere (exFAT, NFS) a link, or a file that can be hard-linked, is still placed without replacing, while a new folder, or a file where hard links fail too, is renamed in once its name is found free, as before, so what appears between the check and the rename (an empty folder; for a file, any file or link) is replaced; a project file that replaces one is refused there before the original moves. An original that goes to a backup on another filesystem is copied, compared entry by entry, and deleted only after skiman notes in its own state (`<state dir>/moves/`, keyed by the original's folder and name) where the complete copy is; a write into the original after the comparison is lost. The note says where one entry's copy is and lets anything be deleted only while it names an existing copy in the backups that holds what is left of that same entry; it is no record of a run. The next move of that entry finishes the move the same way an uninterrupted one ends: it deletes what is left, renames the copy to its own new path in the backups, and deletes the note last; a note whose entry is already gone is left in the state, where nothing reads it. A tmp leftover that holds such an entry is finished before it moves on: what is left of the entry is deleted, and its copy stays where the cut-short move made it. A command that writes several entries is no transaction: killed part-way, it leaves some new and some old. Instead, each write command in the skill repo (`add`, `update`, `remove`, `mv`, `adopt`, `new`, `import`) lists every entry as it should be, in a fixed order, and keeps an entry that already holds it, so running the same command again finishes it from what is on disk (`src/change.rs`); `update` merges from the snapshot its lock entry records, read again from the upstream when `upstream/<name>` does not match it. Three cases are not finished that way, and none loses content: a command killed in its closing sync after the skill repo part is done, whose run again is refused (`mv`, `adopt`, `remove`: nothing is left for it to do there), which `skiman sync` finishes; an update killed after it wrote a merge with conflicts, which is refused until they are resolved and then merges, and conflicts, again; and an update stopped after it wrote `skills/<name>`, before its lock entry, when the run again cannot recognise the merge in place: what it swapped out is no longer in `.skiman/tmp/`, in that run's backup, or among the tmp leftovers a later write command moved to its backup (it was deleted), or the skill or its upstream changed since. That run merges again, taking what is in place as local modifications, and while git recognises upstream's changes already there in most cases, where local and upstream changes sit close together or among repeated lines it can apply one twice or report a conflict. While what it swapped out is there, the run again merges that instead and keeps the merge in place when the two are the same. A folder that is replaced, and a project item, swaps places with its replacement in one rename where the filesystem has one (`RENAME_EXCHANGE`, `RENAME_SWAP`: APFS, ext4, tmpfs, xfs, btrfs), so the path never lacks it; elsewhere (HFS+, exFAT, NFS) the old one is renamed out of the way within the filesystem first, then the new one in, and only then does the old one go to the backup. Either way what came out is checked first, and goes back when it changed since it was read; what that brings out stays in the staging folder, never removed. Killed between the two renames, the path is empty with both versions in the staging folder (the old one beside the new one, with `.skiman-prev` added to its name); only an update run again puts the new one back (before it reads the skill, only into a folder that is still there, and not in a dry run); any other command moves both to the backup, and an `adopt` or `restore` run again writes it from its source, so an entry removed meanwhile stays removed. Sync retargets a link of its own by swapping a new link in with one rename where the filesystem has one, and otherwise, and to remove one, renames it to a temporary name beside it first; either way what came out is removed only while it still points where it did, and otherwise goes back, and what that brings out is removed only while it is the new link, so what took a link's place is never removed. Killed in between, a link left under that name is removed while it points where skiman's own links do (the skill repo; during an `init`, also the repo it replaces): in a tool directory by the next sync, beside an instruction file by the next `skiman sync` (`sync --hook` reads no folder there). One an `init` killed as it changed repos leaves, pointing into the old repo, stays. Content that has to last (the skill repo, project items, machine configuration, backups) is flushed (`fsync`) by whatever wrote it before it is renamed into place, and the folder it goes into after; an original moved within a filesystem is not flushed (skiman did not write it), the folder anything leaves is not, and a folder whose filesystem refuses `fsync` counts as flushed. On Apple platforms, where `fsync` stops at the drive's cache, each device written to is drained once with `F_FULLFSYNC` (plain `fsync` where a filesystem refuses it, as SQLite does) before skiman exits, and before it deletes the only other copy of anything. This asks the system to keep the writes through a crash of the machine or a power loss; it is not tested against one, the order of writes in the drive's cache is not, and a network filesystem keeps what its server keeps. Derived content (links, `managing-skills`, `reported.toml`, the upstream cache) is not flushed: sync rebuilds it. That the skill repo is under git keeps only what was committed.
