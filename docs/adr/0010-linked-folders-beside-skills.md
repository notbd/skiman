# Skills that live outside the canon are registered in it and linked in beside `skills/`

Some global skills have their home outside the canon: a folder of company skills sits in a work directory, is edited there, must not be copied into the canon's git history, and will move to another path. Until now skiman distributed only what the canon holds, so such a folder had to be linked into the tool directories by other means, and skiman reported those links as foreign. skiman now distributes these skills as linked skills. A linked folder is registered in the canon's `skiman.toml` as `[linked.<id>]` with one key, `path`, in the form a project root uses (absolute or starting with `~/`; `<id>` follows the skill-name rule). The folder is read with the rule `skills/` already follows, a folder with a `SKILL.md` is a skill and a folder without one holds skills: a path whose top level holds a `SKILL.md` is one linked skill, named after its id, so that a move that renames the folder changes no name; any other path is read one level deep, where each child folder (or link to one) holding a `SKILL.md` is a linked skill named after that entry, and everything else is ignored. A linked skill must pass the same name checks as any skill skiman distributes and hold a `SKILL.md`; problems inside its frontmatter are warnings, as for the canon's skills. No list of names is kept, so a skill added to the folder is distributed by the next sync and an edit inside a skill needs no sync at all.

Sync makes the links, in two hops. In the canon, `linked/<id>` points to the registered path. In each tool directory, `<name>` points to `<canon>/linked/<id>/<name>`, or to `<canon>/linked/<id>` when the path is itself the skill. `linked/` sits beside `skills/`, holds nothing but these links, and is ignored by one fixed `.gitignore` line, `/linked/`, which `skiman init` and `skiman linked add` write; `linked` or a path under it in the git index is a rule violation. The tool-directory link goes through the canon, not straight to the folder, so that ownership stays what it is today: a property of the link target's shape, with no record per link (`src/ownership.rs`). A link whose target is `<canon>/linked/<id>/<name>` with its own name as `<name>`, or `<canon>/linked/<id>` with its own name as `<id>`, is skiman's. When a `[linked.<id>]` table is deleted, sync therefore still recognises every link it made for it and removes them; when the folder moves, one `path` line changes, sync retargets one link in the canon, and no tool-directory link changes.

The `[linked.<id>]` table is everything the canon records about a linked folder. A linked skill has no `[skills.<name>]` table, no lock entry, no group and no `enabled` key, and `skiman check` warns about a `[skills.<name>]` table that names one and no skill under `skills/`; its summary is read from its own `SKILL.md` ([ADR 0011](0011-linked-skill-summary-in-its-skill-md.md)). To stop distributing a linked folder, delete its table (`skiman linked remove <id>`). To distribute only some of a folder's skills, register those skill folders one by one. Removing a linked folder is one change in one place and leaves nothing behind in the canon. skiman never writes into a linked folder: the commands that act on a skill (`update`, `diff`, `remove`, `mv`) work on `skills/` and refuse a name that is only a linked skill, saying which folder it is edited in, and the commands that create one (`new`, `add`, `adopt`, `import`, `mv` to a new name) refuse a linked skill's name. Project items that overlap a linked folder are neither mirrored nor restored.

The remaining cases follow rules skiman already has.

- **Names.** Tool directories are flat, so a linked skill's name competes with every other skill's. A skill under `skills/` wins over a linked skill of the same name, enabled or not, so that disabling it never hands its name to another skill; between linked folders, the one whose id sorts first wins. The skill that loses is not distributed, and sync and `skiman check` report it. A name that an entry skiman does not own already holds in a tool directory is left alone and reported as occupied, as for any skill.
- **A path that is not there.** The canon is shared between machines and the folder may exist on only one. A linked folder whose path does not exist is reported and skipped like a project root missing on this machine (a path that exists but is not a folder breaks the rules instead) (`docs/project-scope.md`). It then holds no skills, so sync removes `linked/<id>` and its tool-directory links and makes them again once the folder is back. A folder that cannot be read for another reason (permissions, I/O) keeps its links as they are, so a passing failure never withdraws skills.
- **Which paths are allowed.** The project-root rules apply (not `HOME`, `/` or an ancestor of `HOME`; not inside or containing a tool's presence directory; compared by realpath). In addition a linked folder does not contain the canon, is not inside or around any tool directory (Codex's `~/.agents/skills` lies outside its presence directory), and does not overlap another linked folder. These rules hold for the path as written, for every link on the way to it and for its realpath, and the same for a child link, so a path through a link in a tool directory is refused and no link can loop back through skiman's own links. Nor does skiman write into a linked folder by another road: a tool directory, instruction location or hook file that resolves into one is skipped. A linked folder inside a project root is fine. The `skill_dirs` key, which copied such a folder's skills into the mirror instead, is retired ([ADR 0013](0013-retire-skill-dirs.md)).
- **Checks.** `skiman check --staged` reads the git index, so it sees the table and never the linked content: nothing outside git can fail a commit. `skiman check` on the working tree also reads the linked skills, and what it finds there (a folder name that is no valid skill name, frontmatter that breaks the frontmatter rules, a missing summary, a body Antigravity would cut) is a warning that never changes an exit status, because the canon cannot fix it.
- **Display.** `skiman list` shows the kind `linked` and the linked folder. `skiman overview` shows each linked folder as one section after the groups, with its path.

The check that keeps a write out of a linked folder follows one rule: the realpath that was checked is the realpath written to, and a path that is resolved again is checked again. It runs right before each write and again after every wait for the user's answer, so a link on the path re-pointed before that check, or between the check and a sync or init write, is caught. What it does not cover is the staging and swap of [ADR 0005](0005-no-crash-recovery-journal.md) (project items, skills in the canon): a folder on such a path replaced by a symlink in the milliseconds between the last check and the rename is not detected. Closing that would need every write made through folder handles (`openat`) across that protocol.

## Evidence

Measured in scratch folders, and in the real tool directories only with temporary links. The loading tests ran on 2026-11-19 with Claude Code 2.1.328, codex-cli 0.167.2 and agy 1.5.12; the git, link and Claude Code session tests ran on 2026-11-18 with Claude Code 2.1.327. Each test skill held a random token in its description and carried a `metadata.summary` line; each tool was asked, without tools, to quote the tokens it had loaded.

- Claude Code (`.claude/skills/<n>`) and Codex (`.agents/skills/<n>`) loaded a project skill through both link shapes: `<n>` pointing to `<canon>/linked/<id>/<n>` (token `HOPF-71c2e`) and `<n>` pointing to `<canon>/linked/<id>` (token `SOLO-4d9a0`), where `linked/<id>` is itself a link to a folder outside the canon.
- In the real global tool directories (`~/.claude/skills`, `~/.agents/skills`), temporary links of both shapes, removed right after, loaded in Claude Code and Codex (same tokens).
- Antigravity reads global skills from `~/.gemini/config/skills` (also `~/.gemini/skills` and `~/.gemini/antigravity-cli/skills`), not from `~/.agents/skills`. Run with a throwaway `HOME` so that each path was tested on its own, it loaded a real folder, a one-hop link and both two-hop shapes from there; `agy -p '/skills'` prints the loader's own list.
- Antigravity loads a project skill that is a link only when the folder it finally resolves to is inside the workspace, its git repository, or a folder given with `--add-dir`; anything else is skipped without a message (a real folder beside it loaded, token `CTRL-88b1f`). Its 1.5.2 changelog records the same rule for `.agents/skills.json` entries. This is why linked folders are global only, and why project items stay real files (ADR 0006).
- With `/linked/` in `.gitignore`, `git status` lists neither `linked/` nor the links in it.
- After `linked/<id>` is deleted, the tool-directory link's target text still reads `<canon>/linked/<id>/<n>`, which is what lets sync recognise it.
- In a Claude Code session started in the canon, reading or editing a file below `linked/<id>` asks for approval, because the file resolves to a path outside the working directory. A search from the canon's top (`rg`) does not reach linked content, since `linked/` is ignored and its entries are links, unless the path is named. The built-in manual has to tell an agent both, and that `skiman list` shows each linked folder's real path.

## Considered Options

- **Put the links inside `skills/`, so that linked skills sit in groups** (one link per linked folder as a group, or one link per skill in any group): the grouping would be visible, but every reader of `skills/` would have to tell a link from a folder, a link in a group folder made the whole group read as a broken skill when measured, and a group per skill needs a record per skill, which removing the folder leaves behind. Beside `skills/`, ADR 0008 and ADR 0009 stand unchanged and the write commands cannot reach linked content at all.
- **Commit the links**: git stores a link as its target text, a path that holds one machine's user name and is wrong on every other machine.
- **Link the tool directories straight to the folder**: one hop less, but a link to an arbitrary outside path does not say whose it is. skiman would need a record per link, or would lose track of the links of a table that was deleted, and every move would rewrite every tool-directory link.
- **Register linked folders in the machine configuration**: it keeps a work path out of the canon's history, but then the canon no longer says what the setup consists of and every machine is set up by hand. A path that does not exist on a machine is skipped anyway.
- **Copy the skills into the canon** (what the retired `skill_dirs` did for the mirror): a second copy of content that is edited elsewhere, stale between syncs, and company content in the canon's history.
- **A per-skill `enabled` key or a `skip` list in the table**: a second way to select skills. Registering single skill folders already selects them, with no new key.
- **Read a linked folder deeper than one level**: tool directories are flat and read one level deep themselves, and a deeper search would read folders inside a skill as skills.
